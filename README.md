# 订单交付风险分析助手

面向制造业计划主管的订单风险协作产品原型，将订单、包装计划与工单预警组织为可核实、可追问、可跟进的风险事项，帮助用户从发现异常走向证据核对和责任协同。

## 业务背景

判断订单是否需要提前干预，需要结合订单数量、客户交期、公司评审交期、包装安排与工单预警。查到数据之后，计划人员仍需整理判断依据、核实原因，并明确后续由谁处理。

项目围绕四个问题设计核心体验：**优先关注哪张订单、判断依据是什么、还缺哪些信息、下一步由谁核实**。通过风险事项连接分析结果与人工处理，保留业务人员对原因和建议的判断。

## 我的工作

- **明确事实与计算口径**：将未交数与待包装缺口分别定义；包装计划按合同与品名关联，看板指标按合同去重，客户交期与公司评审交期分开呈现。
- **根据数据条件调整范围**：把包装计划完整关联、公司评审交期和理论生产周期列为依赖项，将后续首版方案收敛为订单事实查询、证据与缺口整理、人工确认和指派。
- **拆分分析与处理状态**：将风险结果、建议等级、建议采纳状态和事项处理状态分别管理；采纳建议不直接代表事项已处理，缺失信息也不会因指派而消失。
- **落地可核对的交互**：借助 AI 辅助编码完成会话、看板与详情；为追问范围、原建议留存、人工修改和角色权限补充验收用例。

## 核心体验

### 从自然语言问题进入风险分析

用户可以按合同、产品、客户或时间范围发起查询。回答围绕当前风险组织结论、事实、原因候选、证据缺口与处理建议，并支持继续追问规则依据，保持任务上下文一致。

### 在看板中确定优先核实事项

看板聚合风险订单、临近交期、包装缺口和数据不足等信息，并按合同组织风险事项。用户可按建议等级筛选，区分风险判断、建议等级与处理状态，确定需要进一步核实的对象。

![订单交付风险看板与待处理事项](docs/screenshots/workbench.png)

### 核对证据，形成人工处理决定

详情页集中展示订单事实、包装计划、工单预警、规则依据和待补信息。用户可以修改、采纳或驳回建议，再指派责任人并更新处理状态；原建议和人工操作保留记录。

![风险证据核对与人工决策](docs/screenshots/detail.png)

## 关键迭代：先确认数据能支持什么，再确定首版范围

| 环节 | 具体判断 |
|---|---|
| 发现的问题 | 完整风险研判依赖订单到包装计划的可靠关联，以及公司评审交期、理论生产周期等明确口径；这些条件尚不能全部确认 |
| 判断依据 | 需求梳理与数据调查留下了字段、来源和关联的待确认项，不能仅凭字段名称就把它们当成可用的业务证据 |
| 我的选择 | 在后续需求方案中，将事实查询、缺口说明和人工处理放入首版，把完整风险判断与排序后置；同时明确数据库事实、规则结果、AI解释和内部处理状态的分工 |
| 结果与范围 | 形成了首版与后续能力的划分及对应输入输出、验收条件。公开原型仍保留早期风险流程，用模拟快照验证交互；方案调整与已经实现的能力分别说明 |

原型中的[数量与风险规则](js/rules.js#L92)和[规则边界用例](tests/rules.test.mjs#L12)，展示了如何把判断依赖落实为可核对的计算与缺失提示。

## 验证与评价

已有验证围绕受控样例和业务约束展开：

| 评价问题 | 已有结果与证据 |
|---|---|
| 数量结论能否回到输入事实 | 样例订单数 200、已交数 0、预定数 166，待包装缺口为 34；未交数仍为 200，两者分别解释。见[规则用例](tests/rules.test.mjs#L12) |
| 证据不足时是否仍给出确定判断 | 无关联包装计划时返回“数据不足”，不执行依赖计划的规则；其他合同或品名的计划不能补入当前证据。见[关联与缺失用例](tests/rules.test.mjs#L25) |
| 人工处理是否保留判断过程 | 修改后采纳保留原建议与操作记录；待补信息的事项指派后仍保持待补信息。见[状态用例](tests/state.test.mjs#L35) |

后续计划基于标注样本统计证据引用正确率、缺失信息提示正确率，并通过业务用户任务评估核查完成率和人工修正情况。当前尚无真实模型与真实用户场景的上述统计，规则用例通过不作为模型准确率。

已形成“发起分析—筛选风险—核对证据—确认建议—指派跟进”的交互原型。当前使用模拟快照和本地模板问答，页面操作仅更新浏览器中的演示状态，未接入真实模型及 ERP / MES。

## 技术与运行

原型采用 HTML、CSS 和 JavaScript，按样例数据、业务规则、状态管理、问答和页面展示分层组织。
